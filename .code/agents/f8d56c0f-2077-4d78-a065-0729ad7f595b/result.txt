# Tabbed Inventory Stale-Display Bug: Root-Cause Analysis

## 1. Root Cause

The codebase already has a correct, tab-aware notification API — `GridContainer.NotifyContainerUpdate()` at `GridContainer.cs:1455` — but **it is not used consistently**. The primary item-add packet handler bypasses it, using a direct gump lookup that silently returns `null` for tabbed sub-containers.

### The correct pattern (used by `DeleteObject.cs:68`):
```csharp
GridContainer.NotifyContainerUpdate(world, cont);
```
This first checks for a standalone `GridContainer` window, then walks the item-container chain upward via `FindParentGridContainer()` to find the parent with the tab, and calls `RequestUpdateContentsForTab()`.

### The broken pattern (used by `ItemHelpers.cs:117-119`):
```csharp
GridContainer gridGump = UIManager.GetGump<GridContainer>(containerSerial);
if (gridGump != null)
    gridGump.RequestUpdateContents();
```
`GetGump<GridContainer>(serial)` matches by `LocalSerial`. A sub-container displayed as a tab has no `GridContainer` with its serial as `LocalSerial` — the parent's `LocalSerial` is the root container. The lookup returns `null`, the update is silently dropped.

### Affected Packet Handlers

| Handler | File:Line | Update Method | Tab-Aware? |
|---|---|---|---|
| **AddItemToContainer** (0x25, 0x3C) | `ItemHelpers.cs:117` | `GetGump<GridContainer>(serial)` | **NO — primary bug** |
| DeleteObject (0x1D) | `DeleteObject.cs:68` | `NotifyContainerUpdate()` | YES |
| OpenContainer (0x24) | `OpenContainer.cs:213-239` | `FindParentGridContainer` + tab routing | YES |
| **DenyMoveItem** (0x27) | `DenyMoveItem.cs:45-58` | Calls `AddItemToContainer` (bug) + `ContainerGump` only | **NO** |
| **ObjectHelpers.UpdateGameObject** (0xF7, 0xF3) | `ObjectHelpers.cs:40-43` | `ContainerGump` only, no GridContainer at all | **NO** |
| **EquipItem** (0x2E) | `EquipItem.cs:27` | `ContainerGump` + paperdoll only | **NO** (partially mitigated by `World.RemoveItemFromContainer` calling `NotifyContainerUpdate`) |
| World.RemoveItemFromContainer | `World.cs:635` | `NotifyContainerUpdate()` | YES (safety net) |

**The `AddItemToContainer` gap at `ItemHelpers.cs:117` is the primary cause.** This handler fires for every single item-add packet (0x25) — which is the most common container mutation in gameplay (looting, dropping items, vendor purchases, etc.).

## 2. Reproduction Event Sequence

1. Player opens their backpack → `GridContainer` with `LocalSerial = backpackSerial` is created.
2. Player double-clicks a sub-bag inside the backpack → `OpenContainer.cs` routes correctly, `AddTab(subBagSerial)` is called, sub-bag appears as tab index 1.
3. Player switches to the sub-bag tab (tab index 1).
4. Player drops an item into the sub-bag (drag from world or another container).
5. Server sends packet `0x25` (UpdateContainedItem) with `containerSerial = subBagSerial`.
6. `ItemHelpers.AddItemToContainer()` is called.
7. At line 117: `UIManager.GetGump<GridContainer>(subBagSerial)` → returns `null` because no `GridContainer` has `LocalSerial == subBagSerial`; the sub-bag is a tab inside the backpack's `GridContainer`.
8. **No refresh occurs.** The item is added to the world model but the grid display is stale.
9. Player clicks the "Main" tab → `SwitchToTab(0)` sets `InvalidateContents = true`.
10. Player clicks back to the sub-bag tab → `SwitchToTab(1)` sets `InvalidateContents = true` → `UpdateItems()` runs → item now appears.

The same sequence applies to items being loot-dragged into a tabbed container, items stacked via script, or bulk-add from server events.

## 3. Fix Options

### Option A: Minimal Fix — Replace Direct Lookup with `NotifyContainerUpdate` (Recommended)

**Change:** Replace lines 115-121 in `ItemHelpers.cs`:

```csharp
// BEFORE (ItemHelpers.cs:115-121)
#region GridContainer
GridContainer gridGump = UIManager.GetGump<GridContainer>(containerSerial);
if (gridGump != null)
    gridGump.RequestUpdateContents();
#endregion

// AFTER
#region GridContainer
GridContainer.NotifyContainerUpdate(world, containerSerial);
#endregion
```

**Tradeoffs:**
- (+) One-line change, minimal risk, matches the pattern already used by `DeleteObject.cs:68`
- (+) `NotifyContainerUpdate` is designed exactly for this — tries direct lookup first, falls back to tab routing
- (+) The `world` parameter is already available in scope (`AddItemToContainer` receives it as arg)
- (-) Does not fix the secondary gaps in `DenyMoveItem`, `ObjectHelpers`, or `EquipItem`

### Option B: Fix All Known Gaps

Apply Option A, plus:

**`DenyMoveItem.cs`** — add after line 58:
```csharp
// After the existing ContainerGump update
GridContainer.NotifyContainerUpdate(world, Client.Game.UO.GameCursor.ItemHold.Container);
```
Note: `AddItemToContainer` is also called at line 45 which would be fixed by Option A, but the explicit `ContainerGump` refresh at line 56-58 has no GridContainer counterpart.

**`ObjectHelpers.cs`** — add alongside the `ContainerGump` update at line 40-43:
```csharp
if (Client.Game.UO.GameCursor.ItemHold.Layer == 0)
{
    UIManager.GetGump<ContainerGump>(Client.Game.UO.GameCursor.ItemHold.Container)
        ?.RequestUpdateContents();
    GridContainer.NotifyContainerUpdate(world, Client.Game.UO.GameCursor.ItemHold.Container);
}
```

**Tradeoffs:**
- (+) Comprehensive — closes all identified gaps
- (+) Each change is still small and follows the established pattern
- (-) Slightly larger change surface; the secondary gaps are less commonly triggered
- (-) `DenyMoveItem` comment on line 42 says "Server should send an UpdateContainedItem after this packet" — so the server may re-trigger the fix via the primary path anyway, making the DenyMoveItem fix potentially redundant

### Option C: Centralized Guard — Hook at World Model Level

Instead of patching individual packet handlers, add a `NotifyContainerUpdate` call inside `World.AddItemToContainer()` (or wherever items get parented to containers at the model layer), mirroring the existing `RemoveItemFromContainer` pattern at `World.cs:635`.

**Tradeoffs:**
- (+) Single point of truth — any future packet handler automatically gets tab-aware updates
- (+) Mirrors the existing remove-side pattern
- (-) Higher risk — need to verify that `World.AddItemToContainer` is actually called by all paths and that the container serial is available at that point
- (-) Could cause double-refresh if some callers already do their own notification (e.g., `OpenContainer.cs`)
- (-) Requires deeper investigation of the `World` item lifecycle to ensure no unintended side effects

## 4. Recommendation

**Option A first, then Option B selectively.**

Option A fixes the primary symptom (items not appearing in tabbed views) with a single-line change that exactly mirrors how `DeleteObject.cs` already works. The `NotifyContainerUpdate` API at `GridContainer.cs:1455` was clearly designed for this purpose — its XML doc comment even says _"Use this instead of `UIManager.GetGump<GridContainer>(serial)?.RequestUpdateContents()`"_.

After verifying Option A in-game, apply the `DenyMoveItem` and `ObjectHelpers` fixes from Option B to close the remaining gaps.

Option C is architecturally cleaner but carries more risk for a bug fix and should be deferred to a future refactor if more gaps emerge.
