**Inventory Tab Updates**

- Root cause: `ItemHelpers.AddItemToContainer` (src/ClassicUO.Client/Network/PacketHandlers/Helpers/ItemHelpers.cs:80-140) only calls `UIManager.GetGump<GridContainer>(containerSerial)?.RequestUpdateContents()` after a packet updates an item, so the update is only routed when that container has its own gump. For tabbed containers the `GridContainer` gump belongs to the parent tab window, so `GetGump<GridContainer>(serial)` returns null and `RequestUpdateContentsForTab` never runs. `GridContainer.NotifyContainerUpdate` (src/ClassicUO.Client/Game/UI/Gumps/GridContainer.cs:1451-1465) already knows how to find the parent tab and rebuild the correct tab view, yet `ItemHelpers` never uses it, leaving tab contents stale until the user manually switches tabs (which triggers `RequestUpdateContentsForTab` in `OpenContainer`: src/ClassicUO.Client/Network/PacketHandlers/OpenContainer.cs:211-238).

- Repro steps: enable grid tabs, open a container as a tab inside another (e.g., loot bag tab). While the tab is inactive, drag/drop or loot an item into that container. The normal grid update path in `ItemHelpers` never hits the tab, so the visible list still shows the old contents; only after you click the tab again does `RequestUpdateContentsForTab` fire and the UI refreshes. The same happens when the game drops an item onto the tabbed container via packet.

- Fix options:
  1. Replace the direct `GridContainer` call in `ItemHelpers` with `GridContainer.NotifyContainerUpdate(world, containerSerial)` (source lines ~115-123), so updates go through the helper that knows how to reach both standalone gumps and tabbed children. Minimal change, low risk, reuses existing logic used for removal paths (World.RemoveItemFromContainer already calls `NotifyContainerUpdate`).
  2. Surface a new shared helper in `ItemHelpers`/`World` so every packet-driven container change (add/update/remove) always routes through `NotifyContainerUpdate` regardless of caller. This is more robust but requires ensuring every modifier calls the helper and may need extra refactors.
  3. Keep the current path but detect the tab parent inside `ItemHelpers` (using `GridContainer.FindParentGridContainer`/`HasTab`) before deciding which `RequestUpdate*` to invoke. More code duplication and still risks forgetting future update sites.

- Recommendation: go with option 1—use `GridContainer.NotifyContainerUpdate(world, containerSerial)` in `ItemHelpers` instead of the direct `GridContainer` lookup. It fixes the exact gap, keeps the existing parent/tab detection in one place, and mirrors the delete path that already works for tabs.

- Test ideas: add a regression test (or IME script) that opens a parent grid with tabs, simulates receiving an item-add packet for a non-active tab, and asserts that the tab’s slot manager rebuilds immediately (e.g., verify `GridContainer.RequestUpdateContentsForTab`/`RebuildContainer` is invoked). Manually, repeat the reproduction after the change to confirm the UI shows the new item without switching tabs.
