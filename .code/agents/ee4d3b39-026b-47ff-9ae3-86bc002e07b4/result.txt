## 1) Root cause(s) (with file:line)

**Root cause: tabbed sub-containers don’t have their own `GridContainer` gump, but the item-update path only refreshes a gump by `containerSerial`.**  
When items are added/moved into a container that is currently displayed as a **tab** (i.e., a child container rendered inside a *parent* `GridContainer`), the UI refresh call misses the parent-tab routing, so the visible grid doesn’t rebuild until something else forces a rebuild (tab switch).

Concrete evidence:

- `ItemHelpers.AddItemToContainer` refreshes grid UI only via:  
  `UIManager.GetGump<GridContainer>(containerSerial)?.RequestUpdateContents()`  
  If `containerSerial` is a **tab container** (child), there is **no gump** keyed by that serial → no refresh.  
  See `src/ClassicUO.Client/Network/PacketHandlers/Helpers/ItemHelpers.cs:115`–`src/ClassicUO.Client/Network/PacketHandlers/Helpers/ItemHelpers.cs:121` (esp. `:117-120`).

- The project already contains the correct routing helper for this exact scenario:  
  `GridContainer.NotifyContainerUpdate(world, containerSerial)` which:
  1) updates the gump if one exists for `containerSerial`, else  
  2) finds the nearest open parent `GridContainer` and calls `RequestUpdateContentsForTab(containerSerial)`  
  See `src/ClassicUO.Client/Game/UI/Gumps/GridContainer.cs:1451`–`src/ClassicUO.Client/Game/UI/Gumps/GridContainer.cs:1465`.

- `OpenContainer` *does* handle tab parenting when opening containers, but only for the “open container” event, not ongoing content changes:  
  It finds a parent grid container and updates/adds a tab.  
  See `src/ClassicUO.Client/Network/PacketHandlers/OpenContainer.cs:211`–`src/ClassicUO.Client/Network/PacketHandlers/OpenContainer.cs:239` (esp. `:220-235`).

**Why it shows up specifically as “only visible after switching tabs”**  
Tab switching forces `InvalidateContents = true`, which triggers a rebuild from world state on the next UI update.  
See tab switch ending in `InvalidateContents = true` at `src/ClassicUO.Client/Game/UI/Gumps/GridContainer.cs:1423`–`src/ClassicUO.Client/Game/UI/Gumps/GridContainer.cs:1425`.

**Supporting clue:** removals often *do* update tabs because other codepaths already use `NotifyContainerUpdate`.  
Example: `World.RemoveItemFromContainer` calls it (`src/ClassicUO.Client/Game/World.cs:633`–`src/ClassicUO.Client/Game/World.cs:636`).  
So you can get the asymmetric behavior: removing from a tab updates, adding to a tab doesn’t.

### Option A — Minimal-risk, targeted (recommended minimal)
**Change `ItemHelpers.AddItemToContainer` to use the existing routing helper** instead of directly querying a gump by `containerSerial`.

Where: `src/ClassicUO.Client/Network/PacketHandlers/Helpers/ItemHelpers.cs:115`–`src/ClassicUO.Client/Network/PacketHandlers/Helpers/ItemHelpers.cs:121`

**Pros**
- Fixes the actual mismatch: updates routed to parent tab container.
- Covers *all* callers of `AddItemToContainer` (`UpdateContainedItem`, `UpdateContainedItems`, `DenyMoveItem`, etc.).
- Uses code that already exists and is already used elsewhere (so behavior is consistent with removals).

**Cons / risk**
- `NotifyContainerUpdate` can call `RequestUpdateContentsForTab` on a parent; for **inactive tabs**, current `RequestUpdateContentsForTab` rebuilds immediately (`GridContainer.cs:1487-1494`). If you get bursts of updates into an inactive tab, that could be more work than necessary.

### Option B — Still small, but avoids repeated work in bulk updates
**Do not refresh per item; refresh once per packet** in:
- `src/ClassicUO.Client/Network/PacketHandlers/UpdateContainedItem.cs`
- `src/ClassicUO.Client/Network/PacketHandlers/UpdateContainedItems.cs`

Approach:
- After processing (or after the loop), call `GridContainer.NotifyContainerUpdate(world, containerSerial)` once.

**Pros**
- Avoids N refresh calls when receiving a container content list.
- Less chance of rebuilding inactive tab slot managers repeatedly.

**Cons**
- Must be applied to every packet handler that can add/move contained items (easy to miss one).
- Still leaves other `AddItemToContainer` call sites unhandled unless you update them too.

### Option C — Robust / best UX & perf (slightly larger change)
**Make tab refresh “dirty-flagged” instead of eagerly rebuilding inactive tabs.**

Change behavior in `GridContainer.RequestUpdateContentsForTab` (`src/ClassicUO.Client/Game/UI/Gumps/GridContainer.cs:1475`…):
- If tab is **active**: keep `InvalidateContents = true` (cheap; rebuild next frame).
- If tab is **inactive**: set `tab.NeedsRefresh = true` (new field in `ContainerTab`), *don’t rebuild immediately*.
- When switching to that tab (`SwitchToTab`), if `NeedsRefresh` is set, trigger rebuild.

**Pros**
- Eliminates the biggest downside of Option A (O(N²)-ish rebuild patterns on inactive tabs during item bursts).
- More deterministic UI behavior: active view updates immediately; inactive tabs update when viewed.

**Cons**
- Requires modifying `ContainerTab` structure and tab-switch code paths (more code touched).
- Needs careful handling if you also want some “unread changes” indicator on tabs (optional).
