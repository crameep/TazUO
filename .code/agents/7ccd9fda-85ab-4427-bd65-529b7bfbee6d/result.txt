## Root-Cause Analysis: AutoLoot Targeting Locked House Items

---

### 1. Entry Conditions: When Does AutoLootManager Enqueue Ground Items?

There are two distinct paths. Both require Scavenger to be enabled (`ProfileManager.CurrentProfile.EnableScavenger`).

**Path A — Item Create/Update Event** (`OnItemCreatedOrUpdated`, line 482):
```
OnItemCreated/Updated → CheckCorpse(i) [for corpse items, IsEnabled only]
                      → if EnableScavenger:
                            if IsTrackableGroundItem(i) && Distance <= 20 → add to _nearbyGroundItems
                            if Distance <= AutoOpenCorpseRange → CheckAndLoot(i)
```

**Path B — Position Change** (`OnPositionChanged`, line 417):
```
OnPositionChanged → if EnableScavenger:
                        for each in _nearbyGroundItems:
                            if Distance <= AutoOpenCorpseRange → CheckAndLoot(item)
```

`CheckAndLoot` then calls `IsOnLootList(i)`, which matches ground items against entries that have `Scavenge = true` (line 225: `if (isGroundItem && !entry.Scavenge) continue`).

---

### 2. Guards That Should Prevent Looting Unlootable/House Items

| Guard | Location | What it checks |
|---|---|---|
| `IsTrackableGroundItem` | AutoLootManager.cs:154 | `OnGround && !IsCorpse && !IsLocked` |
| `IsLocked` | Item.cs:61 | `(Flags & Movable) == 0 && ItemData.Weight > 90` |
| `item.IsLocked` in OnPositionChanged loop | AutoLootManager.cs:444 | same heuristic |
| `entry.Scavenge == true` | AutoLootManager.cs:225/238 | per-entry opt-out |
| `_recentlyLooted` dedup | AutoLootManager.cs:121 | per-session, cleared every 5s |
| Cooldown for move failures | AutoLootManager.cs:639 | **only for `!OnGround` items** |

---

### 3. The Core Bug: `IsLocked` Heuristic Does Not Capture Lightweight Locked-Down House Items

**`Item.cs:61`:**
```csharp
public bool IsLocked => (Flags & Flags.Movable) == 0 && ItemData.Weight > 90;
```

**`Item.cs:63`:**
```csharp
public bool IsMovable => (Flags & Flags.Movable) != 0;
```

When a player locks down an item in their house, the server clears the `Flags.Movable` bit (0x20) from that item's entity flags packet. This means `IsMovable == false` for all server-locked items.

But `IsLocked` requires **both** `!Movable AND Weight > 90`. The weight > 90 heuristic was designed to identify heavy immovable world scenery (stone walls, tiles, etc.). Typical house decorations, containers, furniture, and crafted items have `ItemData.Weight` well below 90 — a locked-down vase might have weight 1, a secured chest weight 40, etc.

**The three cases:**

| Item type | `IsMovable` | `IsLocked` | `IsTrackableGroundItem` |
|---|---|---|---|
| Pickupable ground drop | `true` | `false` | ✅ trackable (correct) |
| Heavy immovable scenery (Weight > 90) | `false` | `true` | ❌ filtered (correct) |
| **Lightweight locked-down house item (Weight ≤ 90)** | **`false`** | **`false`** | **✅ trackable (BUG)** |

The `NameOverHeadManager` itself already reflects this 3-way distinction (lines 175–181): `IsLocked`, `IsMovable`, and `!IsMovable` are three separate cases. But `IsTrackableGroundItem` (line 154) only filters on `!IsLocked`, missing the third category.

---

### 4. Exact Lines Responsible

**Primary bug site — the incorrect guard:**
```csharp
// AutoLootManager.cs:154
internal static bool IsTrackableGroundItem(Item item)
{
    return item != null && item.OnGround && !item.IsCorpse && !item.IsLocked;
    //                                                        ^^^^^^^^^^^^
    //  Missing: && item.IsMovable
    //  IsLocked = false for !Movable items with Weight <= 90 (all lightweight locked-down house items)
}
```

**Secondary bug site — same flawed guard used in the position loop:**
```csharp
// AutoLootManager.cs:444
if (item == null || !item.OnGround || item.IsLocked || item.IsCorpse)
{
    (toRemove ??= new List<uint>()).Add(serial);
    continue;
}
// Missing: || !item.IsMovable → lightweight locked items stay in _nearbyGroundItems
```

**Retry cadence — why it repeats every 5 seconds:**
```csharp
// AutoLootManager.cs:545-548 (Update)
if (Time.Ticks > _nextClearRecents)
{
    _recentlyLooted.Clear();   // ← removes the "already tried" dedup guard
    ClearMatchCache();
    _nextClearRecents = Time.Ticks + 5000;
```

```csharp
// AutoLootManager.cs:639
if (!moveItem.OnGround)
    _lootCooldowns[moveItem.Serial] = Time.Ticks + 30000;  // ← only corpse/container items get cooldown
// Ground items (including locked house items) are EXCLUDED from cooldown
```

The retry logic is:
1. House item (incorrectly) added to `_nearbyGroundItems`
2. `CheckAndLoot` matches it → enqueued in `_lootItems`
3. `Update()` dequeues → sends `MoveRequest` → server rejects silently
4. No cooldown set (it's a ground item)
5. Item is still in `_nearbyGroundItems`
6. After 5 seconds, `_recentlyLooted.Clear()` → retry from step 2, forever

---

### 5. Config Issue vs. Code Bug

| Scenario | Classification |
|---|---|
| User has **Scavenger disabled** | This bug does NOT trigger. All scavenger paths are gated by `EnableScavenger`. |
| User has **Scavenger enabled** + loot entries with `Scavenge = true` (default) | Bug manifests. All loot list entries default to `Scavenge = true`. |
| User sets all entries to `Scavenge = false` | Workaround works, but non-obvious. |

**Verdict: Primarily a code bug, secondarily surfaced by config.** The `IsLocked` heuristic is simply wrong for detecting server-locked house items. A user enabling Scavenger for legitimate outdoor use should not need to know about `ItemData.Weight` thresholds.

---

### 6. Proposed Fixes

#### Fix 1 (Minimal, Safe — Recommended first)

**Add `item.IsMovable` check to `IsTrackableGroundItem`:**

```csharp
// AutoLootManager.cs:154
internal static bool IsTrackableGroundItem(Item item)
{
    return item != null && item.OnGround && !item.IsCorpse && !item.IsLocked && item.IsMovable;
}
```

**Also fix the parallel check in `OnPositionChanged`:**
```csharp
// AutoLootManager.cs:444
if (item == null || !item.OnGround || item.IsLocked || item.IsCorpse || !item.IsMovable)
```

**Tradeoff:** Low risk. Non-movable ground items cannot be picked up. The only scenario this could miss is a buggy/private server that doesn't set the Movable flag properly on lootable items, but that's a server defect.

---

#### Fix 2 (Belt-and-suspenders — Defense at move dispatch)

Add a movability check in `Update()` before dispatching the `MoveRequest`, with eviction from the spatial set:

```csharp
// AutoLootManager.cs, inside Update() after line 578:
if (moveItem == null)
    return;

// Guard: if item became non-movable (e.g. locked in house), stop retrying it.
if (moveItem.OnGround && !moveItem.IsMovable)
{
    _nearbyGroundItems.Remove(moveItem.Serial);
    _recentlyLooted.Remove(moveItem.Serial);
    return;
}
```

**Tradeoff:** Defensive, catches items that become non-movable after entering the queue. No functional downside. Good belt-and-suspenders alongside Fix 1.

---

#### Fix 3 (Cooldown for failed ground item move attempts)

Extend `_lootCooldowns` to ground items too, with a shorter window (e.g., 10–15s vs. 30s for corpse items):

```csharp
// AutoLootManager.cs:639 — change condition from !OnGround to always:
_lootCooldowns[moveItem.Serial] = Time.Ticks + (moveItem.OnGround ? 10000 : 30000);
```

**Tradeoff:** Medium risk — the existing comment explains why ground items were excluded: "retry is gated by position changes." Adding a cooldown could slightly delay re-looting a ground item that moves into range after already being tried (e.g., you move away and back). The 10s window is short enough to be non-disruptive. This also prevents spam even if Fix 1/2 somehow misses an edge case.

---

### 7. Server-Specific Differences

On **OSI and most well-implemented shards**: When a player uses `/lock` or the house menu to lock an item, the server sends an updated entity packet with `Flags.Movable` cleared. This means Fix 1 (`item.IsMovable`) correctly identifies locked-down items.

On **some private shards / older emulators** (RunUO, pre-2010 era some custom shards): The Movable flag may not be reliably cleared when items are "placed" or "locked" in a house. In these environments, `IsMovable` may return `true` even for "locked" items, and Fix 1 would not help. Only Fix 3 (cooldown on failed moves) would meaningfully reduce spam — and even then, detection requires noticing the move was rejected, which the client doesn't currently receive explicit feedback for.

**Recommendation**: Apply Fix 1 + Fix 2 now (correct and cheap). File Fix 3 as a follow-up for robustness against server-side Movable flag inconsistencies.
