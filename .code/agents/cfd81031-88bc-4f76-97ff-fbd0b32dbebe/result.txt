Based on my investigation of the `ClassicUO.Client` codebase, here is the diagnosis and recommended fix for the Auto Looter behavior.

### 1. Root Cause Analysis
The primary issue is a flawed heuristic used to identify "lootable" ground items. The `AutoLootManager` relies on the `Item.IsLocked` property to decide whether to ignore a ground item. However, the definition of `IsLocked` in the client is too restrictive for auto-looting purposes.

**Code References:**
*   **The Flawed Guard (`Item.cs` line 61):**
    ```csharp
    public bool IsLocked => (Flags & Flags.Movable) == 0 && ItemData.Weight > 90;
    ```
    This property only returns `true` if an item is both non-movable **and** has a static weight greater than 90 (0x5A). 
*   **The Scavenger Filter (`AutoLootManager.cs` line 154):**
    ```csharp
    internal static bool IsTrackableGroundItem(Item item) => 
        item != null && item.OnGround && !item.IsCorpse && !item.IsLocked;
    ```
    Because many household items (chairs, daggers, clothing, decorations) have a static weight $\le 90$, they are **not** considered "Locked" by the client even when the server has cleared their `Movable` flag (e.g., when they are locked down or secured in a house).

### 2. Why it "Spams"
The system repeatedly attempts to loot these items due to the following flow:
1.  **Detection:** When the player moves or an item is updated, `OnPositionChanged` or `OnItemCreatedOrUpdated` checks `IsTrackableGroundItem`.
2.  **Enqueuing:** Since the item is not "Locked" (weight $\le 90$), it is added to the loot queue.
3.  **Failure:** The client sends a `MoveRequest`. The server rejects it because the item is actually unmovable.
4.  **Retry Cadence:** Unlike container items, ground items in this manager **do not get a long cooldown** upon failure. Instead, they rely on the `_recentlyLooted` cache, which is **cleared every 5 seconds** (`AutoLootManager.cs` line 544).
5.  **Movement Trigger:** Every single step the player takes calls `OnPositionChanged`, which re-evaluates all nearby items. If the 5-second cache has cleared, the looter immediately tries to grab the house items again.

### 3. Diagnosis Summary
*   **Is it a config issue?** No. Even if the user excludes these items manually, the looter still has to iterate and match them against the exclusion list on every step, and any "wildcard" loot entries will still match them.
*   **Is it a code bug?** Yes. The looter should never attempt to move an item that has the `Movable` flag cleared by the server.

### 4. Proposed Fixes

#### Fix A: Explicit `IsMovable` Check (Recommended)
Update the `AutoLootManager` ground filters to respect the `IsMovable` flag directly. This is the safest and most correct fix for the looter.

**Changes:**
1.  Update `AutoLootManager.IsTrackableGroundItem`:
    ```csharp
    internal static bool IsTrackableGroundItem(Item item) => 
        item != null && item.OnGround && !item.IsCorpse && item.IsMovable;
    ```
2.  Update the guard in `AutoLootManager.OnPositionChanged` (around line 444):
    ```csharp
    // Change:
    if (item == null || !item.OnGround || item.IsLocked || item.IsCorpse)
    // To:
    if (item == null || !item.OnGround || !item.IsMovable || item.IsCorpse)
    ```

**Tradeoffs/Risks:** 
*   **Risk:** Extremely low. If `IsMovable` is false, the server will reject the move anyway. 
*   **Benefit:** Immediately stops all attempts to loot house-secured or map-static items that the server identifies as unmovable.

#### Fix B: Redefine `IsLocked` (Higher Impact)
Redefine `IsLocked` in `Item.cs` to simply mean `!IsMovable`.
*   **Risk:** Moderate. `IsLocked` is used by `NameOverHeadManager`, `Pathfinder`, and `GameSceneDrawingSorting`. Changing it globally might change how items are colored in overheads or how the pathfinder treats obstacles. Current logic uses a 3-way distinction (Movable, Locked, and Immovable).

### 5. Recommendation
I recommend **Fix A**. It surgically addresses the `AutoLootManager`'s failure to distinguish between "lootable" and "immovable-but-light" items without risking regressions in the renderer or pathfinding logic. This will completely silence the looter in houses while maintaining its performance on actual loot.
