**AutoLoot Analysis**

- **Enqueue conditions** – On every `OnItemCreatedOrUpdated` and `OnPositionChanged` (AutoLootManager.cs:482‑509 & 417‑467) the manager builds `_nearbyGroundItems` from `IsTrackableGroundItem` (AutoLootManager.cs:152‑155). That helper only lets `item.OnGround`, not a corpse, and `!item.IsLocked` items enter the scavenger set. `OnItemCreatedOrUpdated` immediately calls `CheckAndLoot` when those items are within `AutoOpenCorpseRange`, while `OnPositionChanged` re‑evaluates the snapshot and queues anything still in range via `CheckAndLoot`. `CheckAndLoot` in turn calls `IsOnLootList`, which only matches ground items if the profile entry has `entry.Scavenge == true` (AutoLootManager.cs:220‑242), so only explicitly scavengable entries trigger pickup.

- **Existing guards** – Every ground item is filtered by `IsTrackableGroundItem` (AutoLootManager.cs:152‑155) and later removed from `_nearbyGroundItems` if it leaves range, becomes locked/ a corpse, or disappears (AutoLootManager.cs:421‑469). `IsLocked` on `Item` (Item.cs:61‑65) requires the `Flags.Movable` bit to be clear _and_ `ItemData.Weight > 90`, which was introduced to avoid cluttering the scavenger list with scenery. Corpse/container looting respects `_lootCooldowns` and `_recentlyLooted` to avoid spam (AutoLootManager.cs:120‑140 & 637‑645), but as noted in the comments, ground items skip that cooldown because the assumption is movement change gates retries.

- **Plausible reasons for repeated house attempts** – Locked‑down house furnishings routinely report `OnGround` and stay in `_nearbyGroundItems`, but because their weight is often ≤90 they do **not** satisfy the `Item.IsLocked` heuristic (Item.cs:61‑65). With `EnableScavenger` turned on and a matching `entry.Scavenge`, `CheckAndLoot` will enqueue them every time `OnPositionChanged` fires (AutoLootManager.cs:421‑467). Ground items skip `_lootCooldowns` (AutoLootManager.cs:637‑640), so once `_recentlyLooted`/`_quickContainsLookup` are cleared (AutoLootManager.cs:120‑140 & 564‑580), the same `MoveRequest` is reissued even though the server keeps rejecting it. That produces the “won’t loot this locked house item but keeps trying” behavior.

- **Line/condition pointers** – The problematic heuristics are `IsTrackableGroundItem`/`Item.IsLocked` (AutoLootManager.cs:152‑155; Item.cs:61‑65) plus the ground‑item “retry via movement” loop in `OnPositionChanged` (AutoLootManager.cs:421‑467) and the lack of ground cooldowns when enqueueing MoveRequests (AutoLootManager.cs:637‑640). Because `IsOnLootList` only matches when `entry.Scavenge` is true, the issue only surfaces when scavenger mode is enabled for the offending graphics/regex (AutoLootManager.cs:220‑242).

- **Config vs code bug** – Turning off scavenger (`EnableScavenger`) or removing the `Scavenge` flag from that entry would stop the spam, so user configuration matters. However, the root cause is the heuristic in `IsLocked`: house-locked items have weight ≤90 yet cannot be moved, so `IsTrackableGroundItem` wrongly treats them as lootable. That’s a code bug; the client should treat immovable ground objects as untouchable regardless of weight, otherwise all houselocked loot will keep triggering the queue even though the server always rejects it.

- **Fix ideas**
  1. **Minimum change** – tighten `IsTrackableGroundItem` to require `item.IsMovable` rather than `!item.IsLocked`, or adjust `Item.IsLocked` to drop the weight check so any `Flags.Movable == 0` item is excluded. This stops the client from even considering locked-down house furniture. Risk: some non‑lootable scenery that legitimately lacks the `Movable` bit might also be skipped; verify with scenes that previously showed up in scavenger lists.
  2. **Stronger check** – add explicit filtering based on house multi/container metadata (e.g., skip items whose `RootContainer` is a house multi that is flagged `LockedDown`) or track server replies when a move fails and add a short cooldown/backoff per serial. That prevents repeated retry loops without depending solely on `Flags`.
  3. **Retry policy hardening** – give ground items a failed‑attempt cooldown (mirror `_lootCooldowns` for non-ground items) so even if filtering isn’t perfect, the loop backs off after a rejection. Tradeoff: you might skip a legitimate corpse piece that briefly reports immovable but becomes available; keep cooldown short and clear when the item actually moves.

- **Server variance** – Different shards may not set `Flags.Movable` consistently for locked items, which is why the weight gate exists in the first place. On some servers, an immovable piece might still have `Flags.Movable` set, so any fix relying on that bit must either be conservative (e.g., also check `Item.ItemData.Weight`/`Layer`) or expose a user-facing switch to exempt flagged house items. Without better server metadata (UO doesn’t send a “locked-down” flag in a standard way), heuristics will never be perfect; adding a retry cooldown gives a fallback for shards with inconsistent data.
